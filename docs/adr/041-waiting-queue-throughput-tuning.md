# ADR-041: 대기열 발급 TPS 축소(2명/100ms) 및 폴링 주기 완화(5/3/1초)

- 날짜: 2026-07-10
- 상태: 승인됨
- 관련: [ADR-040](./040-waiting-queue-no-auth.md) (무인증 전환), `docs/domain/waiting-queue/03-performance-test.md` (근거 데이터)

## 결정

1. **Entry-Token 발급 배치를 20명/100ms → 2명/100ms (초당 200명 → 20명)로 축소**한다. `EstimatedWaitPolicy.BATCH_SIZE` 가 스케줄러 배출량과 예상 대기 시간 계산의 단일 소스이므로 이 상수만 변경한다.
2. **클라이언트 폴링 주기를 3/2/1초 → 5/3/1초로 완화**한다 (position >5,000: 5초 / 1,000~5,000: 3초 / <1,000: 1초).

## 배경

성능 테스트 3차 실행(무인증 전환 후, 10,000명)에서 대기열 자체는 설계대로 동작했지만, **발급 초당 200명이 다운스트림 처리량을 압도**하는 것이 확정됐다.

- 다운스트림(주문-결제) 실측 완료 처리량: **초당 ~2건** (결제 콜백 1~5초 + 주문·결제 각 1회 BCrypt)
- 과잉 발급의 3중 피해: ① Entry-Token 1,394개가 주문도 못 하고 TTL(5분) 만료 ② 결제 콜백 대기(평균 41초)가 Tomcat 스레드(max 200)를 점유해 대기열 API까지 연쇄 지연(position p95 30초) ③ 서킷브레이커 OPEN 259건
- 동시 토큰 피크 7,734개 — 발급 속도 ≫ 소비 속도의 직접 증거

### 왜 2명/100ms 인가 (3명이 아니라)

BCrypt 서버 용량이 초당 ~46건(시드 단계 실측)이고, 발급 1명당 주문+결제로 BCrypt 2회가 발생한다.

- 3명/100ms = 초당 30명 발급 → BCrypt 60건/s 필요 → **용량 초과** (2차 실행의 병목 재현)
- 2명/100ms = 초당 20명 발급 → BCrypt 40건/s → 용량 내 + 결제 파이프라인(기존 payment-load 기준 초당 30건 검증)에도 여유

### 폴링 주기 완화 이유

발급이 초당 20명이면 10,000명 소진에 ~500초가 걸려 대기 시간이 10배 길어진다. 뒷순번 유저가 1~3초 간격으로 폴링할 이유가 없고, position 5,000이면 최소 250초를 기다려야 하므로 5초 간격으로도 UX 손실이 없다. 폴링 총량을 줄여 서버 여유를 다운스트림에 양보한다.

## 영향

- `EstimatedWaitPolicy` 계산이 자동 반영된다: `estimatedWaitSeconds ≈ ceil(position / 20)` 초.
- 대기 시간 증가는 의도된 트레이드오프다 — 대기열의 목적은 빠른 입장이 아니라 **다운스트림이 감당 가능한 속도로의 유입 제어**다.
- 토큰 TTL(5분) 내 소비가 자연 보장된다 (발급 즉시 주문해도 다운스트림이 초당 20건을 소화 가능).

## 대안 (미채택)

- **배치 크기 설정값(property)화**: 환경별 튜닝이 쉬워지지만, 현재 단일 환경·단일 인스턴스에서 상수 하나로 충분하다. 재측정에서 다른 값이 필요해지면 그때 도입한다.
- **동적 발급 속도 (다운스트림 부하 기반 조절)**: 서킷브레이커 상태나 결제 지연을 피드백으로 발급량을 조절하는 방식. 명백한 오버엔지니어링으로 배제.
