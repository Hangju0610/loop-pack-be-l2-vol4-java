# ADR-040: 대기열 경로 무인증 전환 (userId 쿼리 파라미터)

- 날짜: 2026-07-10
- 상태: 승인됨
- 관련: [ADR-041](./041-waiting-queue-throughput-tuning.md) (발급 TPS·폴링 주기 조정), `docs/domain/waiting-queue/03-performance-test.md` (근거 데이터)

## 결정

대기열 API(`POST /queue/enter`, `GET /queue/position`)를 `UserAuthInterceptor`에서 제외하고, `?userId={내부 식별자}` 쿼리 파라미터로 요청 주체를 식별한다. 이를 위해 회원가입 응답(`UserV1Dto.UserResponse`)에 내부 식별자 `id`(`USR_...`)를 노출한다.

## 배경

성능 테스트 2차 실행(10,000명, 30초 ramp)에서 **요청당 BCrypt 인증이 시스템 전체 처리량을 초당 ~46건으로 캡핑**하는 것이 확인됐다.

- enter 실패 7,550/10,000 (75.5%, 30초 타임아웃)
- 대기열(Redis) 최대 길이 412 — 유효 유입이 발급 속도에 못 미쳐 대기열은 부하를 받지도 못함
- 즉, "처리량 초과 방어벽" 역할을 대기열이 아니라 의도치 않게 인증 계층이 수행

대기열의 존재 이유는 다운스트림(주문-결제) 보호다. 대기열 진입·폴링이라는 초고빈도 경로에 요청당 수십~수백 ms CPU를 쓰는 BCrypt를 태우면 이 목적 자체가 무너진다.

무인증 전환 후 3차 실행에서 enter 실패 75.5% → 18.8%, 대기열 피크 4,480(이론값 부합), 대기 시간 중앙값 49.5초(설계값 일치)로 대기열이 설계대로 동작함을 검증했다.

## 수용한 리스크

본 프로젝트는 대기열 성능 검증이 핵심 목적이므로 아래 리스크를 문서화하고 수용한다 (요구사항 5-1-1).

1. **신원 사칭 + GT 그리핑**: 타인의 userId 로 enter 를 호출하면 GT 갱신으로 그 유저가 맨 뒤로 밀린다.
2. **entryToken 노출**: 타인의 userId 로 position 을 조회해 토큰을 읽을 수 있다. 단, 주문은 여전히 BCrypt 인증 + 토큰이 모두 필요해 토큰만으로는 행동 불가.

## 대안 (미채택)

- **HMAC 서명 queueToken**: enter 에서 1회 인증 후 서명 토큰을 발급해 폴링에 사용. 보안을 유지하며 검증 비용을 µs 수준으로 낮출 수 있으나, 현 목적 대비 오버엔지니어링으로 판단해 백로그로 남긴다. 실서비스 전환 시 최우선 후보.
- **인증 결과 캐싱**: (loginId, password) 검증 결과를 캐시. API 무변경이지만 평문 비밀번호 비교 결과를 캐시하는 부담과 세션 관리 복잡도가 생긴다.
